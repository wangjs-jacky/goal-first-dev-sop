# Cloudflare 入口选择修复

2026-10-12 · 用户授权“继续排障并修复，再复验”。不换供应商/协议、不新增付费、不动朋友服务器与现有系统代理。

## 分层证据

1. [同客户端经SSH隧道直达源站](../attempts/20261012-1508-绕过CDN对照.md)：6/6 HTTP请求成功，严格校验Origin CA证书。说明此前失败与网络路径有关，不能归因于源站完全不可用。
2. 固定另一个域名A记录172.67.197.16:443复验：ipify成功，Google跟随跳转超时、YouTube/GitHub/trace/再次Google失败，6次仅1次完整成功。V2Ray日志显示 `failed to dial WebSocket`、至该IP的TCP读取 `i/o timeout`；另有已经建立VLESS后数据返回不及时的情形。
3. 改用Cloudflare公共入口104.26.10.229:443，SNI和WS Host仍是node.paws.rodeo：6/6成功，ipify2.033秒、Google4.766秒、YouTube3.114秒、GitHub3.078秒、trace1.992秒、第二次Google4.765秒。所有curl退出0，目标TLS_VERIFY=0。
4. 源站部署时取得的官方Cloudflare IPv4列表包含104.24.0.0/14，覆盖104.26.10.229。该地址是CDN公共入口，不是朋友VPS或其私有域名；所有认证和回源仍用本任务自己的资源。

这是当前Mac mini网络下的路径对照和有效修复，不是Cloudflare全网故障诊断，也没有证明运营商限速或某种封锁机制。相同IP未来可因Anycast路由变化而表现不同，不承诺永久有效。

## 实际变更

新增无凭据 [client-profile.json](client-profile.json) 作为本节点当前连接参数：

| 字段 | 值 |
|---|---|
| 连接地址/address | 104.26.10.229 |
| 端口 | 443 |
| TLS SNI/serverName | node.paws.rodeo |
| WebSocket Host | node.paws.rodeo |
| TLS校验 | 开启，allowInsecure=false |
| UUID与WS路径 | 仍从VPS受限权限配置读取，不进入Git |

03首次连接脚本与04使用验证脚本现在默认读取此profile；后者仍允许指定当前DNS地址做反向对照。域名DNS的橙云A记录仍指向自己的源站，不应把DNS A记录改成这个Cloudflare入口IP，否则会破坏回源。没有修改Cloudflare规则、证书、源站业务配置或防火墙；只在复验时重启新建代理测试服务。

正式客户端导入时必须区分“连接IP”和“TLS/WS域名”：不能把SNI改成IP，不能关闭证书校验。当前已修复保存的连接参数和测试链路，尚未导入Qv2ray、切系统代理或配置其他设备。

## 回退与维护

若此入口后续失效，先保留旧可用代理，用隔离脚本重新比较域名入口及合规可用的Cloudflare入口；验证后更新profile并复验，不盲目关闭TLS。回退profile连接地址为node.paws.rodeo不涉及服务器或DNS变更，但此前失败已证明它在当前网络下不能直接当稳定备用。
