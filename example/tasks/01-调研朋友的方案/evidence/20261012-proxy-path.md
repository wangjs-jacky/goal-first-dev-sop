# 入口与出口链路核验 · 2026-10-12

## 目标与方法

解决本机配置 IP 与朋友服务器 IP 不同的疑点。读取现有配置白名单、解析其中 TLS/WS 使用的域名，并通过现有 HTTP 代理进行两次普通 HTTPS GET。没有修改配置、安装、切换节点或重启。域名、UUID、WS 路径、凭据不保存。

## 实际结果

1. 当前 VLESS 出站：连接地址 `104.26.10.229:8443`，WS + TLS；TLS serverName 与 WebSocket Host 均存在且相同。
2. 上述域名本次 A 解析返回 `172.67.128.89`、`104.21.0.225`。解析结果不等于固定连接地址，但都属于 Cloudflare 网段。
3. 经 `http://127.0.0.1:10802` 请求 Cloudflare 官方 [IP API](https://api.cloudflare.com/client/v4/ips)，success=true。网段匹配：

| 地址 | 官方 IPv4 网段 |
|---|---|
| 104.26.10.229 | 104.24.0.0/14 |
| 172.67.128.89 | 172.64.0.0/13 |
| 104.21.0.225 | 104.16.0.0/13 |

4. 显式通过同一本机 HTTP 代理 GET `https://www.cloudflare.com/cdn-cgi/trace`。返回 ip 与朋友服务器 `104.244.92.199` 完全相等；诊断站点报告本次目标 HTTPS 请求为 TLSv1.3、HTTP/2。这两个字段描述到诊断站点的连接，**不是** VLESS/WS 隧道握手版本的证据。

## 结论与边界

已验证：该本机代理至少对这次 HTTPS 请求可用，目标站点看到的出口是朋友服务器；配置入口 IP 属于 Cloudflare。结合 WS Host / TLS serverName 与用户确认，支持“Mac mini → Cloudflare 入口 → 朋友服务器 → 目标站点”的结构。

没有进入 Cloudflare 账号读取源站配置，也没有检查朋友服务器运行时日志；因此不把中间每一跳、回源模式、回源 TLS 或是否还有中转说成已逐跳验证。不能据单次请求推出所有应用、DNS、防泄漏、速度和长期稳定性均通过。没有读取账号密钥或修改服务。

这是 Task 01 为解释现有链路所做的最小诊断，不代表 Task 02 的完整 POC 已完成。前一份本机检查中“未主动测试、节点关系未知”是当时状态，现由本证据更新。
