## 2. 一次访问经过哪些组件

```text
┌─────────────────────────────────────────────┐
│ 应用：本次是明确指定 SOCKS 代理的 curl 请求   │
└──────────────────────┬──────────────────────┘
                       ↓ 127.0.0.1:10988（测试时）
┌─────────────────────────────────────────────┐
│ Mac mini 的 V2Ray 核心：读取节点并建立连接   │
└──────────────────────┬──────────────────────┘
                       ↓ VLESS + WebSocket + TLS
┌─────────────────────────────────────────────┐
│ Cloudflare 入口：104.26.10.229:443           │
│ TLS SNI、WS Host 都是 node.paws.rodeo       │
└──────────────────────┬──────────────────────┘
                       ↓ 回源 TLS，Strict 校验
┌─────────────────────────────────────────────┐
│ 自有 VPS：192.255.142.217:443 上的 Xray     │
│ 校验节点认证，处理请求，再直接访问目标       │
└──────────────────────┬──────────────────────┘
                       ↓ 出口 192.255.142.217
┌─────────────────────────────────────────────┐
│ 目标网站：通常看到 VPS 出口，不是 CF 入口    │
└─────────────────────────────────────────────┘
```

Qv2ray 是管理本机核心的界面；不打开它，也可以独立启动 V2Ray 核心测试。朋友的 x-ui 是服务端管理面板，我们这次直接管理 Xray 配置与 systemd 服务，没有安装面板。面板不是业务流量必经的一跳。

| 名称 | 在本方案中的作用 |
|---|---|
| VLESS | 表达代理请求、使用 UUID 认证，本身不是这里的加密层 |
| WebSocket（WS） | 将代理数据承载在 CF 可处理的 WebSocket 连接上 |
| TLS | 加密并验证对端；客户端到 CF、CF 到源站是两段连接 |
| VPS / Xray | VPS 是运行机器和出口，Xray 是实际转发程序 |

目标网站自己的 HTTPS 是另一层保护。CF 终止外层 TLS，不能说它完全看不到任何信息；访问 HTTP 目标也不会凭空获得目标站端到端 HTTPS 保护。

这次是应用代理，不是已经验证覆盖全机流量的 VPN。应用是否使用代理、DNS 和 UDP/QUIC 是否走这条链路，需要分别验证。测试使用 SOCKS5h 将目标域名交给代理侧处理，但这不能证明其他应用没有 DNS 泄漏。

## 3. 三种地址不要填混

| 字段 | 本次有效值 | 作用 |
|---|---|---|
| 客户端连接地址 | `104.26.10.229:443` | 选择先连接的 CF 公共入口 |
| TLS serverName / SNI | `node.paws.rodeo` | 指定 TLS 主机名并据此校验证书 |
| WebSocket Host | `node.paws.rodeo` | 指定 HTTP/WS 请求对应的站点 |
| Cloudflare DNS A 记录 | `node` → `192.255.142.217`，橙云 | 告诉 CF 自己的源站在哪里 |
| 目标端看到的出口 | `192.255.142.217` | VPS 直接访问目标时的公网地址 |

**不要把 DNS A 记录改成客户端的 CF 入口，也不要把 SNI 改成 IP。** 橙云记录配置的是源站，而公共 DNS 查询通常返回 CF 地址，这不是矛盾。

其他客户端参数：VLESS、加密 `none`、WS、TLS 开启、`allowInsecure=false`、ALPN `http/1.1`。UUID 和 WS path 从自己服务器的受限配置私密取得，不套朋友的值，不放入 Git。

当前非敏感参数以 [client-profile.json](../03-购买服务器并搭建/notes/client-profile.json) 为准。它不含 UUID 与 WS path，不能单独当完整导入文件。固定入口只是当日当前网络下验证有效，不保证永久稳定。

## 4. 从零搭建的六步

这里把真实操作整理为新手顺序，**未在第二台空白 VPS 上照此重放**。原脚本绑定本次主机并有空配置保护，不可直接重跑；新实例须重新确认架构、版本、端口、供应商与 CF 条款，生成新的凭据。

### 第一步：准备机器与恢复入口

目标：有一台能管理的自有服务器。

本次购买 RackNerd：Debian 12 x86_64、2 vCPU、约 2 GB 内存、35 GB SSD、5 TB/月、洛杉矶 DC03，成交价 US$35.99/年。这是本次记录，不保证未来库存或续费条件，也不是住宅 IP 的证明。

取得地址后核对 SSH 主机指纹，建立专用 SSH 密钥；新开连接确认密钥登录成功，再考虑收紧旧登录方式，保留供应商控制台恢复入口。本次仅做首次信任，未独立比对供应商指纹，旧密码登录未禁用。

预期结果：能独立登录自己的实例，确认不是朋友的机器。

### 第二步：准备域名与证书

目标：客户端能验证 CF，CF 也能验证源站。

使用自己的 `node.paws.rodeo`。VPS 本地产生私钥与 CSR，申请仅包含该主机的 Origin CA 证书，私钥不离开 VPS；证书和私钥保存到 `/etc/xray-node/tls/`，限制读取权限。

为该主机设置 SSL Strict 规则，不改其他 Paws 服务的全域策略。Origin CA 用于 CF 验证源站，通常不被普通浏览器直接信任；不能因直连报错就关闭校验。

预期结果：源站证书链与主机名核验通过，规则只匹配 node 主机。

### 第三步：部署 Xray 核心

目标：程序能读取有效配置并监听业务端口。

本次安装官方 Xray `26.3.27` 并校验固定发布包 SHA256，生成自有 UUID 和随机 WS path，配置 VLESS/WS/TLS 入站 443、直接出站及私网目标阻断。敏感配置在 `/etc/xray-node/config.json`，不进入仓库。

以非 root 的 `xray-node` 用户运行 `xray-node.service`，先校验配置，再启动并设为开机启用。具体配置、权限和命令见 [实际部署脚本](../03-购买服务器并搭建/notes/deploy-node.sh)，它是审计记录，不是通用安装器。

预期结果：配置校验通过、服务 active、443 监听。此时只证明源站运行，不证明端到端可用；enabled 也不等于已做整机重启验证。

### 第四步：限制暴露面并接通 CF

目标：443 经 CF 访问，同时保住 SSH 管理。

本次独立 nftables 表只允许官方 CF 网段访问 443，保留 SSH 22、回环、已建立连接及必要 ICMP。应用前安排自动回退，新开 SSH 验证后才取消回退。已有防火墙必须先分析并合并，不能清空；本次脚本的前提是空规则集。

添加橙云 A 记录 `node` 指向自有 VPS，确认 WebSockets 可用。本路线无需 Worker。CF 网段白名单不等于专属账号认证，仍需节点认证与正确 TLS 配置。

预期结果：SSH 正常、规则生效、CF 能到源站。普通 HTTP 404 只能辅助诊断可达性，不能当代理成功。

### 第五步：隔离验证自己的节点

目标：不影响旧代理，证明新节点能真实转发。

用现有 V2Ray `4.45.2` 启动独立进程，监听 `127.0.0.1:10988`。完整临时配置由非敏感 profile 加自有 UUID/WS path 组成，权限 0600。显式使用该 SOCKS 代理检查出口，再请求完整 HTTPS 页面。

默认域名入口出现过间歇超时，当前有效参数见第 3 节。不能只测端口或只收到 HTTP 头就判成功。

预期结果：请求正常结束、TLS 校验通过、收到完整响应、出口为自有 VPS。结束后停止临时进程并清理凭据。本次隔离测试已通过，日常导入未执行。

### 第六步：验收日常使用并记录

目标：区分“一次连通”和“满足日常需求”。

已测客户端停止/恢复、新代理服务重启恢复、短时重复请求。待做日常客户端导入、指定应用访问、登录/播放、其他设备及长期观察。新增节点时保留旧节点和回退方式，不默认切换全机流量。

每次保存版本、入口、场景、预期、结果与边界，凭据不写入记录。新服务器独立复现也需另行授权，不能为学习重装现有服务。

不是模拟，也不是借朋友节点证明新服务器可用：独立客户端使用自己服务器的真实认证，显式指定其 SOCKS 端口，并核对目标返回的出口。

## 6. 出问题按层排，不要先重装

| 现象 | 优先检查 | 不要误判 |
|---|---|---|
| 本机 SOCKS 连接拒绝 | 临时客户端是否启动、端口是否正确 | 测试清理后是正常现象，不能说 VPS 挂了 |
| 出口仍为朋友 IP | 应用选了哪个代理、当前节点与分流 | 可能根本没走新节点，不是服务器一定配置错 |
| TLS 报错 | 时间、SNI、证书链与域名；区分边缘/源站 | 不用 allowInsecure 掩盖错误 |
| WS 失败或超时 | 入口、WS Host/path、CF 回源及核心日志 | 超时不能直接认定封锁或源站崩溃 |
| 日志 accepted 但页面不完整 | 出站/返回路径、目标响应、客户端行为 | accepted 不代表请求已完成 |
| 只有个别站点失败 | 目标限制、应用协议及分流 | 不直接重装或购买新线路 |

真实排障：默认入口间歇超时 → 固定一个 IPv4 仍失败 → 同客户端经 SSH 隧道直达源站 6/6 成功 → 另一个 CF 入口仅 1/6 完整成功 → 当前入口 6/6 成功 → 完整复验通过。

这支持“当前网络下入口路径差异与失败相关，替换入口实测有效”，没有证明具体运营商、CF 全网故障或某种封锁机制。SSH 对照仍严格验证 Origin CA，没有通过关闭 TLS 制造成功。见 [入口修复记录](../03-购买服务器并搭建/notes/20261012-入口修复.md)。

已确认登录自己的 VPS 后，可做这些只读检查：

```sh
systemctl is-active xray-node node-guard
systemctl is-enabled xray-node node-guard
ss -lnt
journalctl -u xray-node --since '10 min ago' --no-pager
```

日志可能包含私人访问目标，分享前脱敏。active 和监听端口都只是分层证据，不能代替端到端访问。

## 7. 维护与恢复

- 凭据、私钥、完整节点链接/二维码不能进入 Git。无凭据 profile 不能替代敏感配置备份；备份应加密、受限保存，另测恢复。
- Origin 证书到期日为 2041-10-08；私钥泄露要及时轮换。CF 网段是部署日快照，需要维护。
- 日常客户端需要回退时选旧节点。修改服务器前做受限备份，只动本节点，不动其他 Paws 服务。
- 停 `xray-node` 会中断新代理；停 `node-guard` 会删除本次防火墙表、扩大暴露面，只用于必要的紧急恢复，不是常规排错第一步。
- Qv2ray 已停止维护；新旧核心与配置不能假设兼容，升级先做隔离测试。
- CF 不会将机房出口变成住宅 IP，也不保证某个入口永久可用。选型应看实际网络与需求，不只看 CPU 或宣传线路。

具体管理位置、证书与恢复说明见 [03 部署记录](../03-购买服务器并搭建/notes/20261012-node部署.md)。
