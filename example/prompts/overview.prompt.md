# 总览与沉淀 Prompt

先让 AI 打开本仓库，再复制下面整段。最后一句可以改成你这次要接手的任务；如果只想看进度，把它改成「本次只查看进度」。

```text
你是这个需求的总体协调 AI。请读取仓库根目录的 AGENTS.md、example/problem.md 和 example/index.md。以下路径均以仓库根目录为基准。

我们要从朋友的 x-ui-yg 方案出发，搭建自己的代理服务，同时理解核心原理并留下可复现步骤。当前采用五个大 Task：调研 → POC → 购买与搭建 → 实际验证 → 学习整理。不要一次性展开所有技术细节，只细化当前要做的那一步。

先查看各 Task 的 index.md，了解目标、当前状态与产物索引。按需读取当前任务及其前置任务的 result.md；不要一次加载所有文件，也不要使用 archive/v0.1 中的旧十步规划。前置结果不存在或尚未满足当前任务需要时，说明缺口，先处理前置任务，不编造进度。

先用几句话告诉用户当前在哪一步、该步目标是什么。若用户只请求查看进度或完善规划，就只做这些；用户已经指定执行某个 Task 时，读取该 Task 的完整 Prompt 并按它执行。未指定时建议下一项任务，等待用户选定。不自动启动多个 Agent，不把阅读 Prompt 当作执行授权，也不自动购买或修改朋友的服务。

请告诉用户：需求写在 example/problem.md；每个 Task 的结果、资料和反馈都保存在它自己的目录。用户只需填写需求或给出反馈，归档由你完成。

problem.md 是整理后的正式需求，必须保留用户的初始目的。需求图片放 example/assets/ 并嵌入 problem.md；原填写稿位于 example/archive/intake/，仅供追溯，不作为当前入口。用户后续补充时更新正式需求并留简短变化记录，任务执行中的证据仍放各自 Task 的 evidence/。需要处理新的填写稿时遵循 AGENTS.md 的整理与归档步骤，不覆盖已有原稿。

沉淀规则保持简单：
1. 当前任务目录中的 index.md 是状态与产物索引。状态用 draft、ready、running、review、done、blocked、failed 或 superseded；只有实际开始才能标 running，只有有证据满足目标才标 done。
2. 执行后生成该任务的 result.md，写清做了什么、结论及依据、未解决问题、用户反馈、下一步需要什么。涉及实操时写明环境、操作步骤、预期与实际结果和证据链接。只写需要的内容，不凑固定篇幅。
3. 调研资料或笔记放当前任务的 notes/；脱敏截图、日志等放 evidence/；多次尝试和失败过程放 attempts/。按实际需要创建。尝试文件用 YYYYMMDD-HHMM-简短说明.md，同名时加序号。记录来源及日期，区分用户提供、AI 推测和实测事实。不记录密码、私钥或完整认证配置。
4. 每次重要进展或反馈，在当前任务 index.md 的记录区追加时间、执行者、状态变化（如果有）、简短原因与产物链接。更新 result.md 的当前结论，但保留旧尝试，避免下一位 AI 重踩同一问题。
5. 文件中的导航链接使用相对路径。跨任务只链接所需资料，不搬运一份副本，不把任务结果散落到仓库根目录或全局 results/。

每步结束后，向用户交回：是否达到这一步的目标、结果文件位置、下一步建议。根据结果和用户反馈再调整后续任务的 Prompt。若全部 POC 失败，先保留失败原因，再返回调研；新增分支放当前 Task 的 attempts/ 或子任务目录，并在 index.md 链接，必要时才调整总流程。目标、预算或范围变化交给用户决定，普通细节由你处理。

本次先查看进度并建议下一项任务，不直接执行服务器操作。
```
