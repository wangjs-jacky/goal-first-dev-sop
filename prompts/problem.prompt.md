# 问题澄清 Prompt

全局启动入口为根目录 [prompt.md](../prompt.md)；本文件仅用于单独接收和整理需求。

配套模板：[问题清单](../templates/problem.template.md)。先复制并填写模板，再把下方占位路径替换为实际问题文件路径。

本次示例已整理为 [example/problem.md](../example/problem.md)，原填写稿已归档。新需求仍先填写模板；用户提交后重新读取实际编辑的最新文件，整理成正式需求。

```text
本次问题文件：<填写后的问题文件路径>。以下所有路径均相对于仓库根目录。
请读取本仓库 AGENTS.md 与上述问题文件。先用几句话复述我想达到的结果，区分目标、已有方案与未知信息。每轮最多问 3 个真正影响下一步的问题，并解释它们影响什么；不要因为我提到某个工具，就把它当成已确认方案。
目标或验收方式尚未明确时，先与我讨论。我的明确想法可以直接进入可行性核对，模糊部分再协助设计。若必须通过调研才能回答问题，只提出一个边界明确的调研任务。
接收后，先把我的说法整理成需求目录中的 problem.md，保存初始目的、期望结果、已有思路、背景和未知项，保留我的意思，不添加未经确认的目标。图片等附件放同目录的 assets/，在正文对应位置用相对链接展示并注明来源。不要只写聊天附件的临时路径。
需求目录与每个任务目录使用 index.md 做入口并链接具体文件；任务目录使用「两位编号-具体内容」，例如 01-调研朋友的方案、02-POC验证，不加 T 前缀。总览通过这些索引交接工作。
确认正式文件与附件完整后，把原填写稿移入 archive/intake/ 供追溯，从当前入口移走；若归档同名已存在则加日期或序号，不覆盖。空白 templates 母版保留。更新所有任务和 Prompt 的入口为 problem.md；若已有正式需求，则在其中补充并记录变化，不再重复归档。告诉用户正式需求位置及待核实内容，然后再进入规划。
在我确认目标、范围、验收方式后，再列简短 Task：每项 1–2 句话，标明目标、类型、依赖和状态，并附一个可交给独立 AI 的 Prompt。先展示简短流程供用户看方向；用户要求沉淀时，把每个 Task 和完整 Prompt 放到需求目录下的独立任务目录，后续结果也归到对应任务目录，交接与归档统一遵循根目录 prompt.md，不重复生成总览提示词。不自动执行整张任务表。上下文用精确路径按需引用；无法访问资料时说明缺什么，不猜测内容。
```
